# Context Model

> Context is not a conversation history.
>
> Context is a portfolio of information competing for limited attention.

ECC Curator models context as a collection of structured items that compete for inclusion within a finite token budget.

This document defines the core context abstractions used throughout the system.

---

# Design Goals

The context model must be:

- Token-aware
- Model-agnostic
- Explainable
- Extensible
- Optimisable
- Deterministic

Most importantly, every piece of context must be evaluated independently.

---

# Context Hierarchy

```text
Inventory
    ├── Context Item
    ├── Context Item
    ├── Context Item
    └── Context Item
```

A Context Inventory represents everything an agent could potentially send to a model.

A Context Item represents the smallest governance unit.

---

# Context Inventory

The inventory is the complete working set available to ECC Curator.

Examples:

```text
Current Goal
Current Task
Conversation History
Source Files
Git Diff
Terminal Output
Test Results
Project Plans
Retrieved Documents
Agent Memory
```

The inventory exists before governance decisions occur.

---

# Context Item

Every item in the inventory follows a common structure.

```typescript
interface ContextItem {
  id: string;

  type: ContextType;

  content: string;

  tokenCount: number;

  createdAt: string;

  updatedAt: string;

  metadata: ContextMetadata;
}
```

A Context Item is the smallest object that can be:

```text
KEEP
COMPRESS
TRANSFORM
DROP
```

---

# Context Types

ECC Curator classifies information into categories.

## Goal

High-level objective provided by the user.

Examples:

```text
Build a VS Code Extension

Implement OAuth Support

Reduce Context Usage
```

Characteristics:

- Highest retention priority
- Rarely compressed
- Rarely removed

---

## Task

Current work item being performed.

Examples:

```text
Fix login timeout

Implement parser

Refactor scoring engine
```

Characteristics:

- High priority
- Frequently referenced
- Short lifetime

---

## Plan

A sequence of intended actions.

Examples:

```text
Phase 1
Phase 2
Phase 3
```

Characteristics:

- Medium priority
- Good transformation candidate

---

## Memory

Knowledge retained across iterations.

Examples:

```text
API requirements

Project constraints

Technical decisions
```

Characteristics:

- Long-lived
- Frequently evaluated
- Candidate for promotion

---

## File

Source code or project files.

Examples:

```text
README.md

server.ts

package.json
```

Characteristics:

- Expensive
- High value when active

---

## Diff

File modifications or patches.

Examples:

```text
Git diff

Patch file

Generated change set
```

Characteristics:

- Highly relevant during implementation
- Value decreases rapidly over time

---

## Tool Output

Generated by external tools.

Examples:

```text
npm install

git status

docker logs
```

Characteristics:

- Often noisy
- Frequently compressed
- Often ephemeral

---

## Terminal Output

Command-line interaction results.

Examples:

```text
Build logs

Runtime logs

CLI output
```

Characteristics:

- Generally low signal density
- Strong compression candidate

---

## Test Result

Generated by testing systems.

Examples:

```text
Pytest

Jest

Cargo Test
```

Characteristics:

- Often verbose
- Frequently transformed into structured findings

---

## Retrieved Content

External content injected into context.

Examples:

```text
Documentation

Research Notes

Search Results
```

Characteristics:

- Variable lifespan
- Requires active evaluation

---

# Metadata Model

Each Context Item maintains governance metadata.

```typescript
interface ContextMetadata {
  priority: number;

  ageTurns: number;

  references: number;

  source: string;

  compressed: boolean;

  transformed: boolean;

  pinned: boolean;
}
```

---

# Priority

Priority represents the expected importance of the item.

Range:

```text
0.0 - 1.0
```

Example:

```text
User Goal        1.00

Current Task     0.95

Source File      0.90

Recent Plan      0.50

Build Log        0.15
```

Priority influences governance decisions.

---

# Age

Age measures how long an item has existed.

```text
Turns
Minutes
Events
```

Example:

```text
Created 30 turns ago
```

Older items generally lose value over time unless frequently referenced.

---

# References

Tracks how often an item is used.

Example:

```text
Goal         25 References
Task         12 References
Old Log       0 References
```

Frequently referenced items receive additional retention weight.

---

# Context States

Every item exists in one of several states.

```text
ACTIVE
COMPRESSED
TRANSFORMED
ARCHIVED
DROPPED
```

---

## Active

Original information.

Eligible for governance decisions.

---

## Compressed

Information processed by a compression provider.

Examples:

```text
RTK

Caveman

LLMLingua

Troglodita
```

Content remains available but occupies less budget.

---

## Transformed

Information converted into a higher-value representation.

Examples:

```text
Raw Log
    ↓
Failure Summary

Test Results
    ↓
Structured Findings

Large Plan
    ↓
Decision Record
```

---

## Archived

Removed from the active context window but still retrievable.

Examples:

```text
Completed tasks

Historical plans

Old discussions
```

Future versions may provide retrieval capabilities.

---

## Dropped

Removed entirely from the working set.

```text
No retention
No budget allocation
No retrieval guarantee
```

---

# Governance Outcomes

ECC Curator evaluates every item and produces a governance decision.

```typescript
type GovernanceDecision =
  | "KEEP"
  | "COMPRESS"
  | "TRANSFORM"
  | "DROP";
```

---

## KEEP

Preserve unchanged.

Use when:

- Critical information
- High value
- Active relevance

---

## COMPRESS

Reduce token footprint.

Use when:

- Information still useful
- Representation is inefficient

---

## TRANSFORM

Create a better representation.

Use when:

- Raw information is too verbose
- Structured output is more useful

---

## DROP

Remove from the active context.

Use when:

- Low value
- Low relevance
- Budget pressure

---

# Token Budget Allocation

Context items compete for a limited budget.

Example:

```text
Available Budget

Goals                5%
Tasks               10%
Source Files        30%
Diffs               20%
Memories            15%
Retrieved Content   10%
Logs                 5%
Reserve              5%
```

Allocation strategies are defined separately from the context model.

# Guiding Principle

> Every token must justify its existence.

The purpose of the context model is not to store everything.

The purpose of the context model is to help ECC Curator determine what deserves attention.
